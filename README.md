# mise-examples

**mise の設定が何を変えるのかを、入れた場合と入れない場合で測るサンプル集です。**

記事シリーズ「mise 開発環境統合入門」（visionnurture.com）の伴走リポジトリです。

## 2 つの入口

| ディレクトリ | 何があるか | どう使うか |
|---|---|---|
| **`demo/`** | 動くプロジェクトが 1 つ | clone して `mise install` を実行すると、宣言した道具がそのまま手元にそろう |
| **`scenarios/`** | 設定ごとの検証 | 1 つの設定について「入れた場合」と「入れない場合」を並べて測る |

## demo を動かす

```bash
cd demo
mise trust        # [env] を含む設定は信頼の確認が要る
mise install      # mise.toml に書いた道具が入る
mise run hello    # そろった版を表示する
```

`.env` を使う場合は `cp .env.example .env` してから値を書き換えてください（`.env` はコミットされません）。

## scenarios を測る

```bash
bash scenarios/001-install/run.sh
```

結果は `scenarios/<名前>/results/` に出ます。期待する観測は各 `expected.md` にあります。

## 🔴 測るときの落とし穴

**mise は設定ファイルを親ディレクトリへ遡って読みます。**何もしないと、実行した人のホームにある `~/.config/mise/config.toml` や `~/.tool-versions` の内容が混ざり、「設定を入れない場合」にも道具が出てしまいます。

このリポジトリでは `scripts/isolate.sh` がそれを遮ります。

```bash
bash scripts/isolate.sh <測るディレクトリ> ls --current
```

遮り方は 2 つの環境変数の組み合わせです。**どちらか片方では足りません。**

| 環境変数 | 役割 |
|---|---|
| `MISE_CEILING_PATHS` | 指定したパス**自身を含めて**、そこから上を読まなくなる。したがって測りたいディレクトリの**親**を渡す |
| `MISE_GLOBAL_CONFIG_FILE` | 上だけではホームのグローバル設定が残るため、空のファイルへ向けて無効にする |

### 🔴 隔離されないもの

`isolate.sh` が遮るのは**設定の探索だけ**です。次の 2 つは遮られません。

| 遮られないもの | 何が起きるか | どうするか |
|---|---|---|
| **タスクの成果物キャッシュ** | 測り直しても 1 回目からキャッシュに当たり、「走った」と「当たった」の区別が消える | `MISE_CACHE_DIR` と `MISE_TASK_CACHE_DIR` を一時ディレクトリへ向ける（`005-tasks-cache/run.sh`）|
| **インストール先**（`~/.local/share/mise/installs`）| `sync` が書くのはこちら。観測には影響しないが、機械の状態として残る | そのままでよい。ただし件数を突合キーにしない（下記）|

### 🔴 シナリオには 3 つのモードがある

各 `run.sh` の先頭に `# mode:` を書いています。

| モード | 意味 | 全本の再走に含めるか |
|---|---|---|
| **M0** | 追加の道具が要らない | ✅ 含める |
| **M1** | CI で道具を入れて測る | ✅ 含める |
| **M2** | **機械依存**（ホームの nvm・pyenv 等に依存し、clean runner には無い）| 🔴 **含めない** |

**M2 を別のマシンで走らせると、`results/` がそのマシンの値で上書きされます。**
`check:provenance` はモードを見ないため、その瞬間に突合が壊れます。
実際に 2026-09-12、`002-node-sync` の件数キーがこれで壊れました（期待 2 / 別マシンの実測 3）。

**機械の状態から来る件数は、そもそも突合キーにしないでください。**
「何版入っているか」は測る機械の性質で、mise の挙動ではありません。
挙動のほうを真偽値（「全版を取り込んだか」）で押さえ、件数は `results/` の生ログに残します。

## 検査

```bash
npm run check:structure    # シナリオが決まった形を保っているか
npm run check:provenance   # expected.md と実測値が一致するか
npm run check:neutrality   # 公開して困る情報が混ざっていないか
```

`check:neutrality` が見るのは機械で決められる 4 つの型だけです。**公開の前に目で読んでください。**
